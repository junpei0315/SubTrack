# チーム開発ルール

## ブランチ戦略（Git Flow）

### main ブランチ

- 本番リリース用のブランチ
- 直接コミットは行わず、`develop` ブランチからのマージのみ許可

### develop ブランチ

- 開発用のメインブランチ
- 機能開発はすべて `develop` にマージされる
- リリース準備が整ったら `main` にマージ

### feature ブランチ

- 新機能の開発に使用
- `develop` から分岐し、完了したら `develop` へプルリクエストを作成
- 命名規則: `feature/PascalCase`（例: `feature/SubscriptionList`）
- **プルリクエストは自己マージせず、他のメンバーによるレビューとマージを依頼すること**

### hotfix ブランチ（本番のみの緊急修正）

- `main` から分岐し、修正後 **`main` にマージして本番を更新**する
- 同じ変更を **`develop` にも取り込み**、`main` と `develop` の差分が積み上がらないようにする
- 命名例: `hotfix/` で始める（例: `hotfix/fix-payment-timeout`）

## コミットメッセージ

### 形式

```
type: 説明
```

- **日本語で一文**で記述する
- 1つの目的につき1コミット

### タイプ一覧


| タイプ      | 用途               |
| -------- | ---------------- |
| add      | 新機能の追加           |
| fix      | バグ修正             |
| refactor | リファクタリング（動作変更なし） |
| test     | テストコードの追加・修正     |
| chore    | ビルド設定や補助ツールの変更など |
| perf     | パフォーマンス改善        |


### 例

- `add: サブスク一覧画面を実装`
- `fix: 次回請求日の表示がずれる不具合を修正`
- `refactor: サブスク登録フォームのバリデーションを共通化`
- `chore: CI の lint ステップを調整`

## プルリクエスト

- **タイトルは `prefix: 日本語`** 形式で記述する（例: `add: サブスク一覧画面を実装`）
- [`.github/pull_request_template.md`](../.github/pull_request_template.md) に従い、各見出しを埋めてからレビュー依頼する
- 課題管理ツール（GitHub Issues 等）を使う場合は、本文に Issue 番号やリンクを記載し、クローズする関係ならキーワード（例: `Closes #123`）も利用する
- 未完成の共有は **ドラフト PR** を使い、レビュー可能になったタイミングで Ready for review に切り替える
- 自己マージ禁止、他メンバーのレビュー後にマージ

### レビューチェック項目

- コードの可読性・命名規則
- 機能仕様の遵守
- 不要なファイルやコメントの除去
- セキュリティ（認証情報・トークンの扱い、XSS、不正なデータ混入の防止など）

### レビュー・マージ後の運用

- 指摘には対応内容で返信し、修正したらスレッドを解決する（プラットフォームの「Resolve」機能がある場合はそれを使う）
- マージ後、リモートの feature ブランチは削除してよい（リポジトリの既定に合わせる）

## Push前の品質チェック

push 前に **CI と同じ**品質チェックを走らせる pre-push フックを利用できます。

```bash
chmod +x scripts/setup-hooks .githooks/pre-push   # 初回のみ（実行権限が無い場合）
./scripts/setup-hooks                             # 初回のみ（hooks の場所を登録）
```

以降、`git push` 時に **`npm run lint`（Expo ESLint）と `npm run typecheck`（`tsc --noEmit`）** が実行されます。緊急時のみ `git push --no-verify` でスキップ可。

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) でも同じコマンドを GitHub Actions 上で実行します。CI の内容を変えたら **pre-push と手順を揃える**（追記・スクリプト更新）こと。

## 秘密情報・環境変数

- API キー・トークン・パスワードなど機密値を含むファイルはコミットしない（`.gitignore` を運用どおり維持する）
- 必要な環境変数の名前だけを `.env.example` などサンプルに載せ、値は載せない
- ログ・クラッシュレポート・スクリーンショットにトークンや個人情報が写り込まないよう注意する

---

## 依存関係・ロックファイル

- 採用しているパッケージマネージャのロックファイル（例: `package-lock.json`、`yarn.lock`）をバージョン管理に含め、環境間で依存を揃える
- 依存の追加・アップデートは PR で行い、破壊的変更やライセンス上の論点がある場合は説明を書く

---

## リリース

- `main` へマージされた内容が本番リリースの単位になる想定（プロダクトに応じてタグ付けやリリースノートを運用する）
- ユーザー向けの挙動変更や移行手順がある場合は、README やリリースノートに追記する

---

## 使用禁止事項

- ファイル名・変数名に日本語を使用しない
- ファイル名・変数名に特殊文字（`: !@#$%^&*()+=[]{}|;:'",<>/?`）を使用しない
- **AI ツール表記**（`Made with Cursor`、`Made-with: Cursor`、`Co-Authored-By` 等）を**コード・コミット・PR のいずれにも含めない**（co-working 時も同様）
  - 必要なら `commit-msg` フックを別途追加して自動拒否できる（本リポジトリでは未設定の場合あり）
